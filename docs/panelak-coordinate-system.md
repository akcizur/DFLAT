# DFLAT runtime building coordinates

## Authoritative model

The playable building is generated by `src/game/main-building.js`. Its units are metres and its axes are Three.js world axes:

- `X`: facade width, `-14..+14`
- `Y`: vertical, upward
- `Z`: depth, `-28..-16`
- Building plan centre at grade: `(0, 0, -22)`
- Entry facade: `Z = -16`
- Rear facade: `Z = -28`
- Eight occupied storeys at `2.8 m` pitch, with floor datums `Y = 0, 2.8, ... 19.6`
- Roof datum: `Y = 22.4`

For building-local coordinates whose origin is at the centre of the footprint, use:

```text
x_local = x_world
y_local = y_world
z_local = z_world + 22
```

## Geometry corrections

The plinth is now split on either side of the main entrance. Door glazing is attached to the open leaf panels, leaving the walking opening clear. The roof is a separate slab layout with a dedicated 1.05 m square service hatch above the top stair landing, an open lid/frame, and a fixed access ladder. Stair flights are generated for seven transitions between the eight occupied storeys. Lift machinery and the roof vent sit directly on the roof datum.

The facade collision gap uses the nominal 1.82 m door opening. The player controller's collision radius still reduces the reachable centreline width, as expected for a capsule-like player.

## Runtime coordinate export

`createMainBuildingWorld(...)` returns:

- `meshes`: the actual box meshes created for the scene, including rotated stair rails
- `getCoordinateData()`: a fresh structured object with building metadata, object centres, local dimensions, rotations, transformed logical corners, world-axis-aligned bounds, and semantic anchors
- `exportCoordinateCSV()`: CSV rows of type `object`, `corner`, and `anchor`

Example:

```js
const world = createMainBuildingWorld({ THREE, scene, state, ui });
const coordinateJSON = JSON.stringify(world.getCoordinateData(), null, 2);
const coordinateCSV = world.exportCoordinateCSV();
```

Object corners are read from each geometry's vertex positions and transformed by its world matrix. This deduplicates the face-split vertices used by `BoxGeometry`, so exported corners reflect rotations rather than assuming every box is axis-aligned. Bounds are world-axis-aligned bounds, not the original local dimensions.

The object-level `floorIndex` is explicitly marked as an inference from the world-space centre's Y coordinate. It is useful for quick grouping, but it is not a substitute for explicit semantic floor metadata on every mesh. Named anchors carry their own source/formula provenance. Counts are calculated from the live scene each time the export runs, not hard-coded.

## Blender models are separate authoring assets

`tools/generate_socialist_block_17.py` and `tools/VP_OS_Building_Architecture_v4.py` are separate Blender models with different footprints, core layouts, dimensions, and authoring conventions. They are not geometrically identical to the Three.js runtime building. Do not merge their coordinates directly into a runtime export.

For the socialist-block generator, the plan uses Blender's `X/Y` plane and `Z)-up. The orientation mapping into the runtime building's local axes is:

```text
x_local = x_blender
y_local = z_blender
z_local = -y_blender
z_world = z_local - 22
```

This is an axis/orientation conversion only. It does not scale the 16 m Blender footprint to the runtime's 28 m facade, change its chamfered perimeter, or align its stair/lift core. If a single authoritative asset is needed across both runtimes, the Blender model requires a deliberate layout conversion rather than a coordinate-label change.
